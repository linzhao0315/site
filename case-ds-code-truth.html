Kiva's 2026 Ecosystem refresh touched every foundation style and every core component. Somewhere between the 2024 Figma library and the shipped Vue code, the two had stopped agreeing. I set one rule and rebuilt the component layer around it: when Figma and code conflict, code wins.

Role  Principal Product Designer × AI Design Systems Lead Timeline  2026 Scope  5 themes · 5 breakpoints · 10 core components
Chapter 01

Two versions of the truth

Every design system I've inherited has the same quiet problem: the Figma library and the production code start out as twins and drift into strangers. At Kiva the drift had a specific shape. The 2024 library carried button sizes that no longer shipped, hover states the code never implemented, and values with no counterpart anywhere in the codebase. Nobody had lied. The two had simply been maintained by different people, on different schedules, for two years.

Theming made it worse. Kiva runs five visual themes, sometimes on a single page: default, green light, green dark, marigold, stone. The library handled this with per-theme folders of paint styles, and that approach has a flaw no amount of discipline can fix. A Figma paint style bakes in the default mode's value. A style sitting in the "marigold" folder never actually previewed marigold. Designers were picking colors on faith.

  • × The 2024 library and the shipped code disagreed on sizes, states, and values, and there was no protocol for deciding who was right.
  • × 177 theme paint styles that could not do their job. Paint styles always resolve to default-mode values, so the per-theme folders never previewed correctly. They organized the problem instead of solving it.
  • × Phantom states. Hover and focus treatments existed in Figma with no code counterpart. Once engineers knew parts of the spec were fiction, they stopped trusting the parts that weren't.
  • × Every audit finding stalled on the same question: is Figma ahead of the code, or is the code ahead of Figma? Without an answer, cleanup work just moved the inconsistencies around.

The Rule

"
When Figma and code conflict, code wins. Not because code is always right, but because code is what users actually touch. If the code is wrong, we change it on purpose, with a ticket.
Chapter 02

Color without styles

The first structural call was about theming. There were two honest options: keep the style folders and accept that theme previews would stay broken, or move color entirely onto alias variables with five theme modes and delete the styles. I chose the second. Color at Kiva now runs on 41 semantic tokens that resolve per mode, and the 177 paint styles are gone.

Deleting 177 of anything from a production design file is the kind of move that earns you a very tense Slack channel, so the deletion came last, not first. I audited every canvas in the file for style usage and confirmed zero references before retiring a single one. Boring, methodical, and the reason nobody noticed anything except that theme previews suddenly worked.

The same mode mechanics handle responsiveness. Text, spacing, and layout aliases carry five breakpoint modes, and a component's mobile variant pins the mobile mode. A designer drops in the mobile button and it renders mobile values. Nobody has to remember anything, which is the only kind of rule that survives contact with a deadline.

Theming: Before 177 paint styles in per-theme folders, every one previewing default-mode values regardless of what its folder name promised. Adding a theme meant redrawing the entire set and hoping.
Theming: After 41 semantic color tokens × 5 modes. Switch a frame's mode and every fill, border, and text color resolves for that theme. Adding a theme is a new column in a table, not a new library.

Two disciplines keep the architecture from decaying. Literal values live only in the Global collection; everything mapped onto a component is an alias. And every variable is purpose-scoped, so background tokens only ever appear in fill pickers and radius tokens only in corner fields. Chapter 03

Ten components, two strategies

With the foundations settled, I rebuilt the ten most-used product components on top of them: a Mapped variable collection per component group, then canvas components bound to those tokens. Roughly 140 component tokens, every one an alias, zero raw values. I audited the file by machine rather than by eye, which also caught the failure mode manual checks always miss: soft references pointing at deleted variables, which look fine right up until they don't.

For the canvas layer I refused to pick one dogma. Where the 2024 structure was sound, importing and rebinding beat redrawing it. Where 2024 had nothing, or had drifted too far to trust, I rebuilt from the shipped code itself.

Lightbox (12 variants), Footer (3 sizes), Navigation (20 variants across 4 breakpoints and 5 signed-in states). Pulled across files via published-library keys, a route the team assumed required manual copying. Structure preserved, every binding replaced.

Tooltip, chips, pills, carousel controls. The loading spinner was redrawn from the actual SVG paths in the Vue source, and the avatar uses the real Kiva K mark. When Figma has no truth to offer, the component's truth is in the repo.

Chapter 04

Decisions with receipts

"Code wins" does not mean design surrenders. It means the burden of proof is explicit. Reconciliation surfaced six discrepancies between Storybook and the token layer, and all six closed with a written decision instead of a silent tweak. Most were design moving to match code. One went the other way: I pulled tooltips out of the theme system entirely, specced two fixed neutral chips at a 16.1:1 contrast ratio, and engineering opened a refactor ticket against my color definitions. The rule survives because it runs in both directions.

Chapter 05

Documentation that can't rot

Component guidelines die a specific death: someone updates a token, nobody updates the spec page, and six months later the documentation is a museum. I built nine guideline pages in Figma, one per component group, with usage rules, numbered anatomy, spec callouts, and accessibility notes with actual computed contrast ratios rather than a generic "meets AA" stamp.

The part I care most about is the token tables. The swatches on those pages are not drawings of colors. Each one is bound to the variable itself, with variant modes set per column, so when a token value changes the documentation changes with it. The documentation cannot go stale, because the documentation is the token.

Chapter 06

One source, three renditions

The system also ships outside Figma, as a single self-contained HTML file with no build step: interactive foundation panels, live component demos, token tables with full alias chains, and per-panel copy-as-prompt. The same URL serves machines. tokens.json is the single source of truth; tokens.css and the flat markdown files for AI agents follow the llms.txt convention and are generated from the JSON by one script. Updating the entire surface is: edit one file, run one script.

This is the distribution layer for the problem I wrote about in the AI pipeline case study. AI tools were producing off-system UI because the machine-readable surface of the system was incomplete: foundation rules existed, component specs did not. Now any tool can be pointed at one URL and bind real tokens instead of inventing plausible ones.
